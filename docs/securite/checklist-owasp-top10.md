# Checklist OWASP Top 10 (2021)

Pour chaque risque : comment l'application s'en protège, où c'est mis en œuvre
et comment c'est vérifié. Dernière mise à jour : 12 octobre 2026.

| Risque                                         | Protection                                                                                                                                                                                                                                                                                                                                                                    | Vérification                                                                               |
| ---------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------ |
| **A01 Contrôle d'accès défaillant**            | Droits vérifiés côté serveur dans chaque service (`lib/domain/permissions.ts`, `assertCan`) et dans chaque page (`requireUser`). Le rôle et l'état du compte sont relus en base à chaque requête. Les réservations d'autrui sont « introuvables » (pas de fuite d'existence). Masquer un bouton n'est jamais la protection.                                                   | Tests unitaires (matrice des permissions, accès d'autrui), tests e2e `securite`, `comptes` |
| **A02 Défaillances cryptographiques**          | Mots de passe hachés avec bcrypt (coût 12, sel intégré). Session signée et chiffrée par Auth.js (`AUTH_SECRET`). HSTS en production. Aucun secret dans le dépôt (`.env*` ignorés, `.env.example` sans valeur réelle).                                                                                                                                                         | Revue ; `auth-service` (jamais de `passwordHash` renvoyé)                                  |
| **A03 Injection**                              | Accès aux données uniquement par Prisma (requêtes paramétrées) ; seule requête brute : verrou consultatif avec paramètre lié. Mongo : filtres construits côté serveur, `ObjectId` validé. Toutes les entrées sont validées avec Zod. Réponses React échappées (pas de `dangerouslySetInnerHTML`). CSP à nonce contre le XSS. Fichiers téléversés reconnus par leur signature. | Tests e2e (CSP, fichier falsifié) ; tests Zod                                              |
| **A04 Conception non sécurisée**               | Couches séparées, règle ESLint sur les imports, règles de gestion appliquées côté serveur, concurrence traitée par la base (contrainte d'exclusion, verrou par adhérent).                                                                                                                                                                                                     | Tests d'intégration (demandes simultanées) ; ESLint dans la CI                             |
| **A05 Mauvaise configuration de sécurité**     | CSP, `X-Content-Type-Options`, `X-Frame-Options`, `Referrer-Policy`, `Permissions-Policy`, COOP ; `X-Powered-By` supprimé ; bases non exposées en recette ; `SHOW_DEMO_ACCOUNTS=false` hors démonstration ; conteneur de production non root.                                                                                                                                 | Test e2e des en-têtes ; `docker-compose.recette.yml`                                       |
| **A06 Composants vulnérables et obsolètes**    | `npm audit --omit=dev --audit-level=critical` dans la CI ; veille dans [veille-securite.md](./veille-securite.md) ; versions des dépendances figées par le lockfile.                                                                                                                                                                                                          | CI                                                                                         |
| **A07 Identification et authentification**     | Pas d'inscription libre ; message d'erreur identique pour un compte inconnu et un mauvais mot de passe, temps de calcul équivalent ; blocage après 5 échecs par adresse e-mail (et par IP si connue) ; mot de passe d'au moins 12 caractères ; session de 8 h ; redirection après connexion limitée aux chemins internes.                                                     | Tests e2e `securite`, `rate-limiter`, `auth-service`                                       |
| **A08 Intégrité des logiciels et des données** | Dépendances installées depuis le lockfile (`npm ci`) ; images construites par la CI ; tâche planifiée protégée par un secret comparé en temps constant ; migrations versionnées.                                                                                                                                                                                              | Test e2e de la tâche ; revue de la CI                                                      |
| **A09 Journalisation et supervision**          | Journal d'activité (auteur, action, cible, date) en MongoDB, conservé un an ; erreurs inattendues consignées côté serveur sans détail renvoyé à l'utilisateur ; l'indisponibilité du journal est tracée mais ne bloque pas l'action.                                                                                                                                          | Tests `activity`, `resource-service` (journal) ; intégration Mongo                         |
| **A10 Falsification de requête côté serveur**  | L'application n'appelle aucun service externe à partir d'une adresse fournie par l'utilisateur. Seule URL externe : aucune. Les photos sont stockées sur disque, jamais téléchargées depuis une URL.                                                                                                                                                                          | Revue : aucun `fetch` sortant dans le code applicatif                                      |

## CSRF

Les Server Actions de Next.js comparent l'en-tête `Origin` à l'hôte de la
requête ; le cookie de session est `SameSite=Lax`. Aucune action de
modification n'est exposée en `GET`.

## Points restant à traiter

- Limitation des tentatives partagée entre plusieurs instances (aujourd'hui en
  mémoire, voir `RateLimiter`).
- Vérification des en-têtes `X-Forwarded-For` côté reverse proxy en recette.
- Audit externe d'accessibilité.
